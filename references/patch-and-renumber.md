# 在成稿上做增量改稿：补丁脚本与编号顺移

报告已经交付过几轮、读者手里有旧版时，改稿不再是重写，而是在成稿上做增量。这一份管这种改法的操作纪律：怎么改得可核、怎么在加节之后把编号顺移干净、守卫该守哪几条。

## 1　为什么不能直接编辑

成稿动辄上千行、上百个交叉引用。直接动手改，出问题的地方有三类，都是当场看不出来的：

- 读数被顺手改掉。改一段行文时把一个百分比复制错了，没有校验，读到最后也发现不了。
- 表格被重排。编辑器保存时重排了列宽或行尾，一格数据没动，但整表的空白变了，与旧版比对时满篇差异。
- 编号错位。加了一节、挪了一张表，正文里的交叉引用有一部分没跟着改，读者按编号去查会查到别的东西。

所以改稿落成一支脚本，不落成手工编辑。脚本的好处是每一步都写明了预期，跑的时候能对账；手工改的好处是快，代价是不可复核。

## 2　补丁脚本的骨架

一支补丁脚本由三部分组成：一个闸门、一张替换表、几道守卫。

**闸门。** 脚本开头先算目标文件的 md5，与预期值比对，不符就退出、不写盘。这样做的用处是防止在错误的版本上动手——手上如果拿的是上一轮改前的文件，闸门会把它挡下来。改前先把原件另存进 `_backup/`，命名带上日期与轮次。

**替换表。** 每条替换写成三元组（旧文、新文、期望命中次数），跑的时候逐条比对命中次数，不符就退出。期望次数是这套做法里最要紧的一栏：写 1 就必须是 1，出现 0 次说明旧文已经不在（上下文变过），出现 2 次说明替换没有唯一性（会改到不该改的地方）。两者都要停下来看，不要放宽成「至少一次」。

顺序也有讲究。同一批编号要顺移时，**先处理复合引用，再处理单体**。正文里常出现「表 10-3 与表 10-4 都取自……」，若先把表 10-3 改成表 10-4，这句会变成「表 10-4 与表 10-4」；先把「表 10-3 与表 10-4」整串改成「表 10-4 与表 10-5」，再改单处，就不会互相踩。

**守卫。** 替换跑完、写盘之前，过几道结构性的检查。守卫要拦的是「改完看起来对、其实动了不该动的东西」。

写替换表的时候有四个坑，都踩过。行模式的空白写 `[ \t]`，不要写 `\s`——`\s` 会把换行也吃进去，一条替换能跨行吃掉半段。替换要改写同一个累积文本：拿原文那个变量连着替换两次，前一次的改动会在第二次算出来的结果里被丢掉。表格单元格的空白要照原文件逐字复制，凭印象敲空格数对不上，脚本会 0 命中。全局替换会把别的词拆开：把「回答不了」整词换成「无法回答」时，如果旧文写的是「不了」，同一批里含「不了」的其他词会被切开，改完必须回扫全文。

## 3　守卫清单

| 守卫 | 查什么 | 怎么查 |
| --- | --- | --- |
| 行尾纯一 | 没有混进另一种行尾 | 去掉 `\r\n` 之后不应再含 `\n` |
| 表格行保全 | 原有表格行一行没丢 | 旧文的 `|` 开头行逐行在文里找得到；新增行数等于预期 |
| 数字串保全 | 没有读数被改掉或删掉 | 旧文的数字串多重集合是新文的子集 |
| 编号连续 | 顺移之后没有重号或跳号 | 每个节号、表号各恰好出现一次 |
| 禁用词零命中 | 没有带回已清掉的写法 | 禁用词表逐词查 |
| 受保护结构 | 定过不动的东西没动 | 逐条查行数与表号，例如某表恰好十三行 |

数字串保全这条要加一个限定，否则在顺移编号的补丁里必然误报。把表号节号先剥掉再比：

```python
def nums(t):
    t = re.sub(r"10-\d", "", t)   # 表 10-3 → 表
    t = re.sub(r"10\.\d", "", t)  # 节 10.3 → 节
    return re.findall(r"\d+(?:\.\d+)?", t)

lost = Counter(nums(old)) - Counter(nums(new))
if lost:
    raise SystemExit("有数字串消失：%s" % dict(lost))
```

不剥就会这样：`表 10-3` 改成 `表 10-4`，数字「3」少一次；`10.5` 改成 `10.6`，「10.5」少一次。守卫报的是编号换过，不是读数丢了，两者要分开。

编号连续性顺手也查一遍，它同时守住「顺移有没有漏掉某一处」：

```python
for i in range(1, 8):
    assert new.count("### 10.%d　" % i) == 1, i
for i in range(1, 7):
    assert new.count("表 10-%d　" % i) == 1, i
```

## 4　加一节并顺移编号：做几件事

在既有章节中间插一节，牵动的面比想象中大。逐项走一遍：

1. 新节正文与它领的新表。
2. 其后各节的节标题顺移。
3. 其后各表的表题顺移。
4. 正文里所有引用到这些表号的地方顺移（含附录里的引用、附录各节对自己的自引）。
5. 段与段之间的指路句，比如「多数表不足 30 条，正文不展开」——新节如果展开了一项，这句就成了错的，要改成「正文不逐处展开，只把某一项单列出来看」。
6. 章首或摘要要不要加指针，最后再定，别在顺移的半路上加。

第 5 项最容易被漏掉。编号顺移是机械的，脚本能守住；这类「相邻句子与新内容相抵」只有通读的时候才能发现，所以顺移跑完要读一遍新节前后各一段。

## 5　自检脚本怎么组织

一支自检脚本分几类断言，按能否自动判定排序：

- **重跑上一阶段的数值断言脚本。** 上一阶段的脚本如果读的是当前文件，整支重跑一遍就完成了「读数与分组未变」的比对，不必把断言抄一遍。这是最省事也最稳的一类。
- **重跑数据脚本的 `--check`。** 带 `--check` 的脚本只重算不写盘，能证明新节里的数在数据源上仍然成立。
- **由数据源现算新节的每一格。** 不硬编码期望值，现场从清洗后的数据重算一遍，再与正文写法逐格比。硬编码的期望值会随数据更新而失效，现算不会。
- **结构调整查一遍**（第 3 节的守卫清单）。
- **纪律查一遍**：受保护的行数与表号、路径洁净、禁用词、新节自己的边界声明。

有两条判据上的坑，与脚本本身无关但会直接让自查报错号。**位数用半进位算**：一位小数写 `floor(v*10+0.5)/10`，`round` 是银行家进位，`.5` 会往偶数那边靠，算出来的与报告里手写的对不上。**正则要防误命中**：查附录指针的正则别把表内的「12.0%」当成「12.0」这个节号抓走，先限定前缀（「见 12.」「详见 12.」）再匹配。

上一阶段的脚本如果是「改前件 vs 改后件」的比对型（比如逐行比对表格行），它的基线会停在那一次改稿上，此后不再适用。遇到这种，把那支脚本**冻结成历史件**——把它的两个路径都指向那一轮改前与改后的备份，让它从此只复现那一次改动；当前文件的守卫交新的脚本承担。不要为了让它绿而反复放宽它的阈值，那样它就既不守历史也不守现在。
